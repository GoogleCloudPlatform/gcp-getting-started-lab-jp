# j5-eks-microservices: the equipment marketplace (fictional) migration test bed

This directory is **realistic test material for the `migration-to-gcp` skill** in this repository. It models "the equipment marketplace (fictional)", a Tokyo equipment-rental marketplace that re-platformed onto Kubernetes in 2022: two microservices (`ems-catalog-api`, `ems-booking-api`) on an EKS cluster in AWS ap-northeast-1, described in [`architecture.md`](./architecture.md).

Difficulty: **hard** — the resource count is modest, but the workload topology is split across two authoring layers (see "Dual-layer convention" below) and pod identity is wired through IRSA, both of which resist naive IaC-only analysis.

## What's in here

| Path              | Purpose                                                                                     | Used by                                                             |
| ----------------- | ------------------------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| `terraform/`      | Authoritative, deployable IaC for the **infrastructure layer**: EKS cluster + node group, IAM/OIDC/IRSA, DynamoDB, 2x ECR | AWS deploy AND the skill's Discover phase              |
| `k8s/`            | Authoritative manifests for the **workload layer**: namespace, deployments, services, pod service account | `scripts/deploy.sh` (envsubst -> `k8s-build/` -> `kubectl apply -k`) |
| `app/catalog-api/`| Go 1.24 inventory service — stdlib `net/http` only, embedded deterministic catalog          | Built into an image by `scripts/deploy.sh`; runs on the cluster      |
| `app/booking-api/`| Node 22 / Express booking service + public API gateway                                      | Built into an image by `scripts/deploy.sh`; runs on the cluster      |
| `scripts/`        | `deploy.sh`, `seed.sh`, `smoke-test.sh`, `teardown.sh`                                      | Operator / harness orchestration                                     |
| `k8s-build/`      | Rendered manifests (generated by `deploy.sh`, gitignored)                                   | `kubectl apply -k` / `kubectl delete -k`                             |
| `.migration/`     | Created by the skill at runtime — do not commit, do not gitignore                           | Phase outputs: resource inventory, target design, generated IaC      |
| `.iteration-log/` | One subdirectory per harness iteration                                                      | Observation logs and transcripts for the outer iteration loop        |

## Dual-layer convention (Terraform + k8s manifests)

The real customer splits their estate the way most Kubernetes shops do:

- **Terraform owns the infrastructure**: cluster, node group, IAM roles, the OIDC provider + IRSA role, the DynamoDB table, and the ECR repositories. This is the only layer visible to IaC scanners — the skill's Discover phase detects Terraform (`**/*.tf`) and CloudFormation markers, and has **no parser for Kubernetes manifests**.
- **Kubernetes manifests own the workloads** (`k8s/`): the `ems` namespace, both deployments, the `catalog-api` ClusterIP service, the `booking-api` service account carrying the IRSA role annotation, and the `type: LoadBalancer` service from which the cluster's cloud controller provisions the public NLB.

Consequence for any IaC-only inventory: the **entire runtime topology is invisible** — which containers exist, their replica counts and env wiring, the internal `booking-api -> catalog-api` call path, which pod identity is bound to the IRSA role, and even the network edge (the NLB appears in no Terraform file). Unlike `sample-project`'s dual-write convention (where ecspresso files are mirrored by authoritative shadow CloudFormation), **there is no shadow copy here**: `k8s/` is the single source of truth for the workload layer, exactly as the customer maintains it. Anything that inventories this project must read both layers.

`deploy.sh` renders `k8s/` with `envsubst` (exactly three placeholders: `${ECR_REGISTRY}`, `${IMAGE_TAG}`, `${IRSA_ROLE_ARN}`) into `k8s-build/` and applies that with `kubectl apply -k`.

## Out-of-scope dependencies

These appear in `architecture.md` but are NOT modeled as AWS resources here:

- **Marketplace web front-end** (mermaid Internet subgraph): the customer's Next.js storefront, run by a different team. Simulated by `scripts/seed.sh` and plain `curl` against the API edge.
- **Payment provider webhook** (mentioned in architecture.md history): stubbed out of this extract entirely — bookings are stored as `confirmed` without a payment leg.

## Deployment

Requires `terraform`, `aws`, **`docker` and `kubectl`** (plus `envsubst` from gettext).

```bash
# Pre-flight: ~/.aws/journeys.env must define EXPECTED_ACCOUNT_ID and
# AUTOTEARDOWN_DATE. Every script sources it and aborts on account mismatch.
aws sts get-caller-identity   # confirm the right account before any create

./scripts/deploy.sh           # terraform apply + build/push 2 images +
                              # kubectl apply -k + rollout + NLB wait
                              # prints BASE_URL=http://<nlb-dns-name>

./scripts/seed.sh       "$BASE_URL"   # 3 deterministic bookings
./scripts/smoke-test.sh "$BASE_URL"   # PASS/FAIL per check, nonzero exit on failure
```

### Deployment notes (lab account)

- First `deploy.sh` run takes **~20-25 minutes**: the EKS control plane alone is ~10 min, the node group ~5 min, and the NLB another few minutes after the manifests land. Re-runs converge in a few minutes.
- Everything runs in the account's **default VPC** via Terraform data sources; the stack never creates or deletes VPCs/subnets. Nodes are 2x on-demand `t3.medium` in public subnets (no NAT gateways anywhere).
- Idle cost is dominated by the EKS control plane (~$0.10/h) and the two nodes (~$0.11/h combined) plus the NLB (~$0.02/h); DynamoDB is PAY_PER_REQUEST and idles at zero.

## Verification endpoints

Both are served by booking-api at the NLB edge (catalog routes are proxied through the same edge, so one BASE_URL exercises everything):

- `GET /health` — dependency substatus JSON (persistence + internal catalog hop), always HTTP 200.
- `GET /admin/aws-check` — pod-identity parity dashboard `{overall, checks: {dynamodb, sts}, account_suffix}`; `scripts/smoke-test.sh` asserts `overall == ok`. This page proves the **pod's** credentials (not the node's) can reach the table.

## Resource tagging convention

Every AWS resource created by Terraform carries (via the provider's `default_tags`):

- `Owner=migration-test`
- `CostCenter=test-journeys`
- `AutoTeardown=YYYY-MM-DD` (from `AUTOTEARDOWN_DATE` at deploy time)
- `Journey=j5-eks-microservices`

To find every resource later: `aws resourcegroupstaggingapi get-resources --tag-filters Key=Journey,Values=j5-eks-microservices --region ap-northeast-1`. Caveat of the dual layer: the **NLB is created by the cluster, not by Terraform**, so it carries `kubernetes.io/*` tags instead — `teardown.sh` handles it explicitly.

## Teardown

```bash
./scripts/teardown.sh   # type "yes" at the prompt, or FORCE_TEARDOWN=1
```

Deletes the `booking-api` Service **first** and polls until its NLB is really gone (a cluster destroyed before its Services orphans the load balancer), then removes the workload objects and finally `terraform destroy`s the infrastructure layer. The default VPC and subnets are data sources and are never touched.
