# azure/j3-aks-microservices: AKS microservices migration test bed

Realistic test material for the `azure-to-gcp` skill in this repository. The estate belongs to a fictional
regional parcel operator in the east region whose tracking system was rewritten onto AKS in 2022 — two
small services, a Service Bus queue, a Cosmos DB container and a federated pod identity — described in
[`architecture.md`](./architecture.md).

Difficulty tier: **hard**. The resource count is modest, but the estate is authored across two layers
that are maintained by different people (see "Two authoring layers" below), pod identity is wired through
Entra workload identity federation rather than any credential, and the datastore is Cosmos DB, whose
target on the other side is a design decision rather than a lookup.

**There is no `discovery/` and no `costs/`.** This estate has never been through an Azure Migrate
assessment — there are no virtual machines in it to assess — and the contractor reads the invoice in the
portal rather than exporting it. Everything discoverable about the estate is in the two authoring layers,
the application code, and `architecture.md`.

Evaluation criteria and scoring live in the repo-root `CATALOG.md`.

## Two authoring layers (Terraform + Kubernetes manifests)

The operator splits its estate the way most small Kubernetes shops do, and the split follows the people:

- **Terraform owns the platform** (`terraform/`): the cluster and its node pool, the container registry,
  the Service Bus namespace and queue, the Cosmos DB account, database and container, the user-assigned
  identity, its federated credential, and every role assignment. The contractor who owns the subscription
  maintains this and nothing else.
- **Kubernetes manifests own the workloads** (`k8s/`): the `tracking` namespace, the `akm-workload` service
  account carrying the identity's client-id annotation, both deployments with their replica counts and
  environment wiring, and the `type: LoadBalancer` Service from which the cluster provisions its public
  address. The two developers maintain this and nothing else.

There is no shadow copy of one layer in the other: `k8s/` is the single source of truth for the workload
layer, exactly as the customer maintains it. Anything that inventories this project has to read both.

`deploy.sh` renders `k8s/` with `envsubst` (exactly five placeholders: `${ACR_LOGIN_SERVER}`,
`${IMAGE_TAG}`, `${WORKLOAD_IDENTITY_CLIENT_ID}`, `${COSMOS_ENDPOINT}`, `${SERVICEBUS_NAMESPACE_FQDN}`)
into `k8s-build/` and applies that with `kubectl apply -k`.

## Deployment

Requires `az`, `terraform`, **`docker` and `kubectl`** (plus `envsubst` from gettext).

```bash
# Pre-flight: ~/.azure/journeys.env must define EXPECTED_SUBSCRIPTION_ID,
# AUTOTEARDOWN_DATE and AZURE_LOCATION. Every script except seed.sh sources it and
# aborts on mismatch.
az account show --query id -o tsv    # confirm the right subscription before any create

./scripts/deploy.sh                 # terraform apply + build/push 2 images +
                                    # kubectl apply -k + rollout + load-balancer wait
                                    # prints BASE_URL=http://<lb-ip>

./scripts/seed.sh       "$BASE_URL"   # 3 fixed parcels
./scripts/smoke-test.sh "$BASE_URL"   # PASS/FAIL/SKIP per check, nonzero exit on failure
```

First `deploy.sh` run takes roughly 10-15 minutes: the AKS control plane and the registry's second region
dominate, and the load balancer needs another few minutes after the manifests land. Re-runs converge in a
few minutes.

The stack is idempotent — `terraform apply` converges and `kubectl apply -k` is create-or-update — and
there is nothing to rotate on a re-deploy, because the estate has no passwords, connection strings or
account keys anywhere. The pods reach Cosmos DB and Service Bus with a federated Entra identity, and the
registry is pulled with the cluster's kubelet identity.

Three names are resolved at deploy time rather than hard-coded, because all three are globally unique
across Azure: the container registry (`akmacr<uniq>`), the Service Bus namespace (`akm-sb-<uniq>`) and
the Cosmos DB account (`akm-cosmos-<uniq>`). The suffix is derived from the subscription id and the
resource group name, so it is stable for a given lab.

### Region, node size and role assignments

All three are settable at deploy time, because none of them is the same in every subscription:

- **Region.** `var.location` has no default. `deploy.sh` exports it from `AZURE_LOCATION` in
  `~/.azure/journeys.env` (as `TF_VAR_location`) and refuses to run without it. Exactly one region name
  appears in `terraform/`: `var.acr_replication_region`, the second region the registry replicates into.
  That one is a property of the estate rather than of the subscription it is stood up in — it was chosen
  when the western depot was still on the cards — so it stays in the platform code. A registry cannot
  replicate into its own region, which a precondition on the registry checks at plan time; if the
  platform is being stood up in that same region, override it:

  ```bash
  AKM_ACR_REPLICATION_REGION=<any other region> ./scripts/deploy.sh
  ```

- **Node size.** `var.node_vm_size`, default `Standard_D2s_v5`. Which sizes a subscription can actually
  create varies by region, quota and offer type, so it is swappable without editing anything:

  ```bash
  AKM_NODE_VM_SIZE=Standard_D2as_v5 ./scripts/deploy.sh
  ```

  Terraform cycles the pool through a temporary one (`temporary_name_for_rotation`) when the size
  changes, so a resize needs enough quota for both pools for a few minutes.

  **Arm64 fallback.** Where no x64 general-purpose size is available, `Standard_D2pds_v5` (Arm64,
  2 vCPU / 8 GiB) is a working substitute — both services are Go and Node, neither Dockerfile pins an
  architecture, and `golang:1.25-alpine`, `gcr.io/distroless/static-debian12` and `node:22-slim` all
  publish arm64 variants. Pick the size from the
  [Dpsv5, Dplsv5 or Epsv5 series](https://learn.microsoft.com/azure/aks/use-arm64-vms): those are the
  only Arm64 families AKS takes, so the Arm64 burstable sizes (`Standard_B2p*_v2`) are not an option —
  and B-series of any architecture is refused for the pool that carries `kube-system`, which here is the
  only pool. The images must be built for the same architecture as the nodes, or the pods crash-loop on
  an exec-format error:

  ```bash
  AKM_NODE_VM_SIZE=Standard_D2pds_v5 AKM_IMAGE_PLATFORM=linux/arm64 ./scripts/deploy.sh
  ```

  Cross-building arm64 on an x64 workstation needs QEMU registered with Docker
  (`docker run --privileged --rm tonistiigi/binfmt --install arm64`) or a native arm64 builder; a
  multi-arch `docker buildx --push` works equally well, but a single-arch build matching the pool is
  enough here. Switching architecture is the one change that cannot be rolled onto a live cluster — AKS
  will not move an existing pool between x64 and Arm64, so run `./scripts/teardown.sh` first.

- **Role assignments.** Writing an Azure role assignment needs Owner or RBAC Administrator on the scope;
  Contributor is not enough. Where the deployer holds only Contributor, `AKM_DEPLOY_ROLE_ASSIGNMENTS=false`
  stands the platform up without the four grants in `terraform/identity.tf`. That leaves the estate
  half-built rather than working: the kubelet cannot pull the images, and the pods cannot reach Service
  Bus or Cosmos DB, so the rollout never completes and every `/admin/azure-check` subcheck fails until
  someone with the rights re-runs with the flag on (the default).

### Two resource groups

Terraform puts everything it creates in `akm-rg`. AKS creates a **second** group, `akm-nodes-rg`, named
by `node_resource_group` in `terraform/aks.tf`, and owns it: the node VMs, the cluster's own virtual
network, and the load balancer and public IP that the `tracking-api` Service asks for all live there.
That group is not in the platform code and must not be edited by hand. Teardown handles both — see below.

## Verification

```bash
./scripts/smoke-test.sh "$BASE_URL"
```

Fifteen checks: nine over HTTP and six against the Azure control plane. The HTTP ones are
provider-agnostic, and the same invocation is the acceptance test for a migrated GCP deployment of this
workload:

- `GET /health` returns 200 with `status: ok`.
- `GET /admin/azure-check` returns `overall: ok`, plus one subcheck each for `identity`, `cosmos` and
  `servicebus` — the parity dashboard, proving the **pod's** federated credential can reach each service.
- A parcel round trip: `POST /parcels` then `GET /parcels/{id}`, plus a 404 for an unknown parcel.
- The asynchronous leg: the scan event published by that `POST` has to be consumed by the worker, which
  stamps `notifiedAt` on the document. This is the only check that exercises the messaging pipeline end to
  end, and it polls for up to 90 seconds.

The remaining checks read the Azure control plane (cluster state, the `apps` node pool, workload
identity, the registry, the queue's session setting, and the Cosmos DB container). Those skip themselves,
rather than failing, when `akm-rg` is not present in the current subscription, so the script stays usable
against a GCP target.

Where `AKM_DEPLOY_ROLE_ASSIGNMENTS` is anything but `true`, none of the nine HTTP checks can pass: the
kubelet cannot pull either image, so no workload is running to answer them. They report `XFAIL` and do
not fail the run. `deploy.sh` treats the same posture the same way — a rollout wait that times out is a
loud warning rather than a fatal error, so the deploy still finishes and still prints the `BASE_URL` this
step needs. The six control-plane checks still have to pass — the platform itself deploys fine without
the grants.

## Resource tagging

Every taggable resource Terraform creates carries `Owner=migration-test`, `CostCenter=test-journeys`,
`AutoTeardown=<from env>`, `Journey=azure/j3-aks-microservices`. Find them later:

```bash
az resource list --tag Journey=azure/j3-aks-microservices -o table
```

Caveat of the two-layer split: the load balancer and the public IP the Service adds to it are created by
the **cluster**, not by Terraform, so they carry the cluster's own `kubernetes.io/*` tags instead and will
not appear in that list. The node VMs do carry the tags, from the `default_node_pool` tag block in
`terraform/aks.tf`.

## Teardown

```bash
./scripts/teardown.sh   # type "yes" at the prompt, or FORCE_TEARDOWN=1
```

Deletes the `tracking-api` Service **first** and polls until its public IP is really released — a cluster
destroyed before its Services can leave the group delete stuck on `PublicIPAddressCannotBeDeleted` — then
removes the remaining workload objects, then runs a single `az group delete` on `akm-rg`. Deleting the
group deletes the cluster, and deleting the cluster deletes `akm-nodes-rg` with it; the script waits for
that cascade and fails loudly if the node group survives, rather than leaving node VMs billing quietly.

Deleting rather than stopping matters: a stopped AKS cluster still holds its node VMs and still consumes
regional vCPU quota.
